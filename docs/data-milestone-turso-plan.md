## 4. Client choice (your Q3/Q5) — the verdict

**Use Turso libSQL.** It *is* libSQL + is the Turso client (one artifact `tech.turso.libsql:libsql:0.1.0`), supporting remote query, local file, **embedded replica + `sync()`**. That's strictly better than "generic SQLite-only remote" (there is no such thing) and than JDBC (absent on Android).
- **Remote reads** → `Libsql.open(url, authToken).connect().query(...)`.
- **Local/offline** → open the identical libSQL/SQLite **pack fragment** files locally. **No sync.** (Turso's embedded-replica/`sync()` exists but is deliberately NOT used — users are read-only; canonical DBs change only by admin import. Sync would be for local-first read/write replicas, which isn't our model.)
- **SQLite vs libSQL?** Don't frame it as either/or: **libSQL underneath, SQLite-compatible SQL + FTS5 above**. Use the libSQL client for the Turso boundary; plain SQLite reads for local files.

**Risk (must document to Shah):** it's a **Technical Preview, Android-only, pre-1.0** for the *remote client*. **Validate on device before building on it**: local fragment opens; FTS5 external-content `MATCH` works; remote read-query latency is acceptable. Keep `SqlBackend` thin so a future stable SDK (or dropping the remote client and serving **GH packs + HTTP `/v2/pipeline`** instead) is a small swap. **Turso Sync / embedded-replica / partial-bootstrap are NOT in the user path at all** (no sync — users read-only, admin imports), so none of them gate the design.

## 5. Secrets & tokens — production standard practice (your Q7/Q8/Q10)

**Threat model:** the corpus is **GPL/public** — a read-only token leaks the ability to `SELECT` data that is *already public on GitHub*. So the read token is **semi-public**, not a crown jewel. The **admin/group-write token** (`KHUSHU_TURSO_API_TOKEN`) can `destroy`/write → **never in the app, never in a repo** (CI-only). GitHub itself warns mobile secrets are extractable (`mobile-secrets-warning` in the Turso docs) — we assume the read token **will** be extracted and design accordingly.

**Read path (the only token the app needs):**
- Create **per-DB, `--read-only`** Turso tokens (`turso db tokens create khushu-<x> --read-only`) — not one group token — so a leak of one pack endpoint can't touch the others.
- Inject via **CI secret → `BuildConfig`/resource at build time**; nothing hard-coded, nothing committed (Khushu already `commit.gpgsign=false`, `.env`/`.turso-local` gitignored). Local dev uses a gitignored `local.properties`.
- Keep the token out of the shipped mapping/proguard output; reference only from the `TursoRemote` class.

**Rate limiting (your concern: stop someone spamming the key to bulk-dump):**
- **Reality:** free Turso instance shows `Rate Limits: null` = plan defaults, configurable per-DB but **not granular per-end-user** on free. Turso enforces plan throughput caps (reads rows/requests), and the preview SDK's request volume is the practical governor.
- **The bulk-dump vector isn't the token — it's GitHub** (the packs/assets are public anyway). Rate-limiting the token does not and need not stop dumping *public* data; and GPL means we can't really. So the design goal is **protect Turso spend + keep the app snappy**, not "prevent copying public corpus."
- **Best-practice levers, in order:**
  1. **Local packs (prebundled + downloaded) = steady-state local reads** (near-zero Turso traffic). This is the biggest limiter and the perf win — **no sync involved**; a deleted pack is re-fetched from GH (or falls back to remote query), not replicated.
  2. App-side: cache pack fragments; never re-download a present verified pack; backoff on error; **don't fan out whole-table SELECTs remotely** (query by pack/ayah/FTS — bounded).
  3. Keep **read-only + per-DB scoping** (blast-radius).
  4. If real abuse/quotas ever needed: **Turso external auth providers / fine-grained permissions** (JWKS per-user tokens) minted by a tiny backend — or move the token to a **runtime-fetched short-lived token**.
- **Paid/private tier (D10, standing rule):** when user-specific or paid content ships, **mint short-lived per-user tokens server-side at runtime; never bake a long-lived key.** The public read-only token stays for the public corpus only; private data uses the auth'd user path (§7).

**Rotation (do now, before we wire the app — destructive, needs go):**
1. `turso group tokens invalidate` (or per-DB `turso db tokens invalidate`) → kills the token printed earlier + all derived.
2. Recreate **per-DB `--read-only`** tokens for the app (the admin `KHUSHU_TURSO_API_TOKEN` stays separate, CI-only).
3. Store new read-only tokens only in the secret store (CI secret + gitignored local.properties).

## 6. Branching before rotation (your Q9) — expert opinion

**Rotating tokens does NOT touch data** — `invalidate` only kills auth tokens; rows are untouched. So no backup is *required for the rotation itself*. Branching is still worth it, for other reasons:

- `turso db branch <src> <dst>` = cheap copy in-group (free plan: 6/1000 DBs, 859MB/5GB used — huge headroom), with **`--timestamp` point-in-time**.
- **Recommendation:** create a **`dev`/`staging` branch** per core DB (or a single `khushu-snapshot` set) as (a) a safety net for the **schema migrations** the user-data DBs + any pack-fragment rebuild will need, and (b) a place to prototype **writes** without risking prod reads. This is normal DB dev hygiene, not a prerequisite for the (safe) token rotation. Do the rotation regardless; do branching as you set up the **user-data** work.
- Keep **content DBs immutable/versioned-by-release** (re-import a new versioned DB, don't mutate) — branching is for the *mutable user-data* DBs, not the corpus.

## 7. User-data DBs (your Q9 forward-looking)

Bookmarks/streaks/bio/gender/etc. are **writes + private** — a different topology from the read-only public corpus:
- **Separate DB(s)**, e.g. `khushu-users` (or per-user scoping), with **per-user auth**, **never** the public read-only token, ideally behind a **short-lived runtime token** (§5 D10) once there's a backend/account.
- **Privacy:** user rows are not public → the read-only-public-token model does **not** apply; must authenticate the actual user (app sign-in / device key / Supabase-style auth we already use for feedback) then scope reads/writes.
- Free tier is fine for **dev/branching**; move user-data to a production instance + real auth + backups before real users write to it.
- Keep the **thin** `SqlBackend` so content(read-only, local-first) and user-data(auth'd, write) are two clearly separate clients — don't merge them.

## 12. First orchestrator PR — concrete design (needs Shah's eyes on the seam)

Toolchain verified: `khushu-orchestrator` compiles + tests offline (`./gradlew --offline :orchestrator:compileTestKotlin` exit 0) and already `api`s `org.xerial:sqlite-jdbc:3.46.1.0` with a working read pattern in `LocalHadithRepository`.

**The one architectural call:** the orchestrator is **JVM-only** and sqlite-jdbc bundles a *desktop* native lib that does NOT load on Android (exactly why `LocalHadithRepository` can't run in-app today). So the seam must abstract at the **query** level, never expose `java.sql.Connection`:
```kotlin
// NEW com.khushu.data.libsql (additive; no existing public API touched)
interface SqlStore {
  suspend fun query(pack: PackRef, sql: String, args: List<Any?> = emptyList()): List<Row>
}
// JVM/test impl: JdbcSqlStore (sqlite-jdbc, mode=ro&immutable=1) — reusable now
// Android impl (in app): LibsqlSqlStore over tech.turso.libsql:libsql 0.1.0 — NOT androidx.sqlite (no FTS5). Same SDK also does remote: Libsql.open(url, token).
```
- `LocalPackStore` opens `data/packs/<id>.db` via `SqlStore`.
- `TursoStore` runs the SAME sql remotely — **prefer HTTP `/v2/pipeline`** (already validated; avoids the preview-SDK dependency), libSQL client optional/later.
- `PackManager` = install/verify(sha256)/delete from `packs.json`; deleted pack → its queries route to `TursoStore`.
- `AssetResolver` = `asset_id → release_name → KHUSHU_ASSET_URL_TEMPLATE`.
- Migrate repos one domain at a time (quran first), **keeping** `model/plans/adaptive/markup` + public signatures; retire `data.transport` only after its repo is migrated.
- **PR #1 (purely additive, zero app breakage):** `libsql` package + `JdbcSqlStore` + unit test over the real `quran-core.db` (surahs/ayahs/arabic-FTS MATCH) → proves the end-to-end contract. **PR #2:** migrate Quran repo. **App PR:** wire `AndroidSqlStore` + downloads/settings.

**Why this is the stopping point, not "blocked":** the Android local-runtime gate is closed (libSQL passes, androidx.sqlite fails). The remaining design work is now mechanical: (a) add positional-access to the orchestrator `Row` (libSQL `Rows` yields `List<Any?>` without column names), (b) implement `LibsqlSqlStore` (single class for local file + remote url+token) in the app, (c) migrate Quran repo + downloads/settings.
